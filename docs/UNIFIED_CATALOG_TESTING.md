## Исправления, проверенные при интеграции

- ID модели зависит от repo, immutable revision и выбранного комплекта файлов. Разные веса одного репозитория не конфликтуют и не используют один локальный профиль.
- Совпадение repo/revision с исходной подборкой не заменяет выбранные пользователем файлы seed-моделью. Детали Hugging Face сохраняют полный серверный список; дедупликация поисковых карточек не является выбором весов.
- Краткая пауза ограничения частоты search → detail выполняется в worker с ограничением до секунды и не блокирует HTTP event loop. Ошибка сети остаётся видимой; кнопка обновления сохраняет фильтры.
- Настоящий вес выявил старый формат `weight_g/weight_v`. Поддержка этих точных эквивалентов добавлена без fallback на небезопасный pickle. QA дополнительно обнаружил неоднозначность mixed old/new представлений относительно настоящего Torch load hook; смешанный комплект теперь отклоняется и проверяется отрицательной fixture внутри теста архитектуры. Отдельные корректные legacy и modern варианты остаются допустимыми.

## Серверная граница доверия

Renderer отправляет provider, ID и выбранные известные пути. URL, размеры, SHA-256 и immutable revision берутся из серверных метаданных, а не из тела запроса. Серверный кеш с TTL 600 секунд допустим для закреплённых файлов: это не клиентское `canInstall`. После истечения TTL неудачное обновление может показать сохранённые сведения, но новая установка по устаревшему fallback блокируется. Сохранённая избранная карточка браузера также не предоставляет право устанавливать произвольный файл.

HTTPS/allowlist и каждый redirect проверяются отдельно; веса не идут через loopback с внешним токеном. Сохраняются проверки SHA-256/размеров, безопасного ZIP, структуры PyTorch/FAISS и атомарного появления модели. `weights_only=True` и проверки метаданных не являются OS sandbox сторонних нативных парсеров и не гарантируют безопасность любого файла. FAISS размерности 256/768 не доказывает происхождение индекса из конкретных весов.

## Повторение автоматических проверок

Из `engine`:

```powershell
.venv\Scripts\python.exe -B -m unittest discover -s tests -p "test_unified_catalog_security.py" -v
.venv\Scripts\python.exe -B -m unittest discover -s tests -p "test_catalog_security.py" -v
.venv\Scripts\python.exe -B -m unittest discover -s tests -p "test_*.py" -v
```

Из `app`:

```powershell
npm run typecheck
npm run build
node --test tests/main-lifecycle.cjs
node --test tests/cable-setup.cjs
node tests/ui-regression.cjs
```

Для UI нужны Playwright и Chrome/Chromium; пути при необходимости задаются через `PLAYWRIGHT_MODULE` и `BROWSER_EXECUTABLE`. Автотесты движка создают уникальное временное хранилище через `_test_env.py`; пользовательские модели и записи для них не используются. Дополнительные команды состава/экспорта и аппаратные сценарии — в [TESTING.md](TESTING.md).

## Следующая ручная приёмка

На разрешённых локальных данных проверить установленную Windows-сборку: поиск, выбор точного файла, загрузку/отмену/повтор, перезапуск и сохранение, A→B→A, preview, удаление только выбранной тестовой модели. Затем последовательно проверить одну фразу и показатели `inferMs`, `realtimeFactor`, `inputDrops`, `outputUnderruns` на CPU и поддерживаемой NVIDIA. Отдельно проверить Discord/кабель. Все новые результаты фиксировать с устройством, режимом и ограничениями; успешную установку Nyamura не называть проверкой качества речи.

GitHub, удалённые PR и публикация релиза этим QA не затрагивались. Веса и записи не включаются в исходники или установщик.
